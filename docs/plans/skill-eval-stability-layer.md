# Development Plan: Skill Eval — stability layer (repeat + variance + noise-aware alert)

- **Spec:** docs/specs/SPEC-2026-07-12-skill-eval-stability-layer.md
- **Execution mode:** single-agent

## Context

The MERGED differential skill-eval scores each case **once** per suite run
(`SkillEvalRunExecutor.run` loops `snapshot.caseIds` a single time, then pools via
`poolSuite` → `setTerminal`). But both delta arms are LLM calls, so a
`recall`/`precision`/`citation_accuracy` from a single run carries hidden variance
the product never surfaces, and the v1 regression alert (skill-diff AC-27) compares
two *versions* — it cannot tell "real regression" from "LLM noise within one
version".

This feature ports the harness eval method (N runs → `mean ± stddev`, a `flaky`
band, a `non_discriminating` signal, an "indicative only" caveat for small n) into
the in-product skill-eval — **without** changing the differential model, the delta
computation, or the scoring math. A *stability group* repeats ONE frozen snapshot N
times over the UNCHANGED `SkillEvalRunExecutor`, then a pure-code aggregator reports
per-metric variance, per-case `flaky` / `non_discriminating` flags, and a
noise-aware structured alert that dampens the existing regression banner by the
sampled stddev. Goal restated: answer "is this skill's delta stable, or did I just
draw a lucky/unlucky sample?".

## Requirements review & recommendations

The spec is **approved** (11 ACs, zero `[NEEDS CLARIFICATION]` items). The four
scope-defining decisions are pre-resolved and embedded as UD-1..UD-4 (repeat/variance
defaults, group persistence, structured alert shape, group-compare out of scope) —
they are NOT re-opened here. Every AC is testable and consistent with the merged
codebase; no blocking findings. Execution mode is **single-agent** (given): one
implementer works the phases top-to-bottom; phases order the work by dependency and
are NOT split into disjoint parallel slices, so there is no context pack.

**Recommendations (non-blocking, folded into the tasks):**

- **(impl) Compute-on-read, do not denormalize.** The group table stores only the
  snapshot identity + `n_requested` + `status`; `EvalSkillStabilitySummary`,
  `EvalSkillCaseStability[]`, and `EvalSkillStabilityAlert` are DERIVED at detail /
  dashboard read time from the child `eval_skill_suite_runs` rows + their per-case
  `eval_runs`. The aggregation is pure O(n × cases) code (AC-11). This keeps the
  migration minimal: one new table + one nullable FK column, no stats columns.
- **(impl) Keep `scoring.ts` byte-for-byte.** AC-7 is a WRAPPER, not an edit. Reuse
  `regressionAlert`'s exact "largest ≥1pt drop over the two latest completed runs"
  rule via a NEW pure helper `worstMetricDrop` living in the new `stability.ts`; the
  band wrapper `noiseAwareAlert` consumes it. `regressionAlert` / `adaptSkillAlert`
  stay unchanged and the string `EvalSkillDashboard.alert` is preserved (UD-3).
- **(impl) Same-unit band comparison.** Express both `move` and `band` in percentage
  points (pts). `regressionAlert` already speaks in pts (`3pts`); a metric's band =
  `round(stddev × 100)` pts, so `beyond_band = move > band` is a same-unit compare.
- **(impl) Reuse the resolved snapshot verbatim.** The stability executor calls the
  existing `resolveSkillSnapshot` ONCE and passes the SAME `SkillSuiteSnapshot`
  object into every one of the N `skillExecutor.run(...)` calls — that is exactly
  what makes AC-2 (no mid-group leak) hold, for free, from the differential AC-12
  freeze.

## Risks & mitigations

- **Migration not applied before integration tests.** `*.it.test.ts` provisions
  schema via `runMigrations` (test/helpers/pg.ts), so T6 MUST generate the migration
  file (`pnpm db:generate`) or every stability integration test 500s with `relation
  "eval_skill_stability_groups" does not exist`. The implementer generates the file
  (SQL emission, not application); it does NOT run `pnpm db:migrate`. For the dev DB, a
  human runs `cd server && pnpm db:migrate` (MANUAL, AGENTS.md gotcha).
- **Modifying the reused executor.** AC-2 depends on `SkillEvalRunExecutor` staying
  UNCHANGED and being handed the SAME snapshot object every iteration. The stability
  executor must only CONSTRUCT/REUSE it, never edit it; guard with a unit test that
  asserts identical snapshot reference across the N `.run` calls.
- **Editing `scoring.ts` for the band.** AC-7 is a wrapper; `regressionAlert` /
  `adaptSkillAlert` and the string `EvalSkillDashboard.alert` must stay byte-for-byte
  (UD-3, agent back-compat). The band lives in the new `stability.ts::noiseAwareAlert`;
  `pnpm arch:check` + the unchanged agent-dashboard tests are the backstop.
- **Doubled-then-multiplied LLM cost.** A group is `2 × N × cases` LLM passes.
  Mitigated by `STABILITY_MAX_N = 5` (UD-1), the `EVAL_RUN_RATE_LIMIT` (10/min) on the
  start route, and SEQUENTIAL execution of the N child runs (bounds provider
  concurrency).
- **Barrel edit vs "never edit the barrel".** One `export *` line for a NEW file is
  the sanctioned additive extension (the differential feature added the identical line
  for `eval-skill-suite.js`); it does not touch existing exports.
- **Untrusted diff / skill body.** Repetition adds NO new external contact: each child
  run re-invokes the same provider path as a normal review, and the whole
  variance/flag/alert path is pure code with no LLM (AC-11).
- **Client suite runs on the WSL ext4 mirror** (`bash scripts/test-mirror.sh client
  test`), never `pnpm test` from `/mnt/e` (TD-010); package suites run STRICTLY
  SEQUENTIALLY.
- **Evals gate N/A.** This touches contracts/schema/UI but NOT `.claude/skills` or
  `CLAUDE.md`/`AGENTS.md`, so the `evals/` harness gate does not apply; the green
  barrier is the package suites (server unit + integration, client) + `pnpm arch:check`
  + `node scripts/sync-shared.mjs --check`.
