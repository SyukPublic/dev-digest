# Development Plan: Skill Eval Pipeline — differential (delta) evaluation of review skills

- **Spec:** docs/specs/SPEC-2026-07-12-skill-eval-differential.md
- **Execution mode:** multi-agent

## Context

L06 shipped an in-product regression harness for review **agents** (run an agent
over its cases, read pooled recall / precision / citation with trend, compare,
and a code-computed regression alert). The data model was seeded owner-generic
(`eval_cases.owner_kind` is `skill | agent`) but the `'skill'` owner is dormant —
the service throws `"Only agent eval cases are supported"`.

This feature activates the dormant `'skill'` owner via a **DIFFERENTIAL execution
model**: a skill has no model/prompt/strategy, so it is only meaningful as a
delta on a host agent's review. To evaluate a skill on a case, pick a host agent,
run its review **twice** over the case's stored diff + PR meta — WITHOUT the skill
(baseline arm) and WITH the skill added to the host's linked skills — then score
the **delta** (findings the skill caused: present WITH, absent WITHOUT). It reuses
L06's engine path, contracts, pure-code scorer, dashboard idioms, and the
owner-neutral Case Editor, adding only the skill-suite parent shape, one new
shared contract file, and the two-arm executor. Goal restated: shift the same
trend-first, pure-code methodology from "is this AGENT better?" to "is this SKILL
pulling its weight?".

## Requirements review & recommendations

The spec is approved (33 ACs, zero open questions). All scope-defining decisions
were pre-approved and are embedded below as hard design choices — they are NOT
re-opened here.

**Resolved design decisions (from the caller, baked into the plan):**

1. **Skill suite parent = a NEW sibling table `eval_skill_suite_runs`** (never add
   nullable skill columns to the agent-typed `eval_suite_runs`). Shipped agent
   rows stay untouched.
2. **Second suite-parent linkage on `eval_runs`.** Per-case rows currently FK
   `suite_run_id → eval_suite_runs`. Rather than drop that FK, this plan adds a
   **second nullable FK column `skill_suite_run_id → eval_skill_suite_runs
   (onDelete: cascade)`** (Phase 2 / T5). Rationale: additive (new column, own
   migration — server rule §"new columns = their own migration"), never edits an
   existing migration, PRESERVES the agent path's DB-level cascade, and gives the
   skill path its own DB-level cascade (AC-31). A per-case skill row sets
   `skill_suite_run_id` and leaves `suite_run_id` NULL; the two are mutually
   exclusive by construction (a service invariant, not a DB CHECK).
3. **Persist ONLY the delta in `eval_runs.actual_output`** (the WITH-arm findings
   attributable to the skill, each carrying a `caught|noise|ignored` classification
   for the delta view). No baseline/with raw-arm drill-down. `actualFindingCount`
   (helpers.ts:77) reads `.findings` → works unchanged on the delta shape.
4. **`/eval` tab selection via URL params:** a `?tab=skills` discriminator
   alongside the existing `?agent=`, plus `?skill=<id>` for the per-skill
   dashboard deep-link — mirroring the current thin `?agent=` switch in
   `client/src/app/eval/page.tsx`.

**Recommendations (non-blocking):**

- **(impl) Reuse the L06 scorer verbatim over the delta.** The differential path
  needs NO new scoring math. Build a synthetic `CaseRunResult` whose `findings` =
  the delta grounded findings, `dropped` = the delta pre-gate dropped count, and
  `costUsd` = the summed both-arm cost, then feed it to the EXISTING `scoreCase` /
  `poolSuite` (`scoring.ts`, unchanged). This satisfies AC-13/AC-14/AC-15/AC-16/
  AC-18 for free and keeps the pure scorer single-sourced. This is the central
  reuse of the plan.
- **(impl) Reach the skill body / `skill_versions.body` via a thin read on the
  eval module's OWN repository** (server/INSIGHTS 2026-07-04: `container.skillsRepo`
  does NOT exist; the skills repo is module-private). Do NOT `new SkillsRepository`
  and do NOT deep-import it.
- **(spec, minor) AC-32** already holds with no code change: `cascadeAgentDelete`
  only deletes the agent's own cases + agent suites; skill suites where that agent
  was host carry `host_agent_id` with no FK and are untouched. T27 is a
  **regression test** locking this in, not new deletion logic.

### Reused pure scorer — feed it the DELTA (scoring.ts, UNCHANGED)

The differential path reuses these VERBATIM. Signatures (server/src/modules/eval/scoring.ts):

```
export interface CaseRunResult { expected: EvalExpectedOutput; findings: Finding[]; dropped: number; costUsd: number | null; }
export function matchesExpectation(finding: Finding, expected: EvalExpectedFinding): boolean  // file EQ && range INTERSECT (scoring.ts:73)
export function scoreCase(result: CaseRunResult): CaseScore                                   // per-case pass + nullable metrics (scoring.ts:146)
export function poolSuite(results: CaseRunResult[]): SuiteScore                               // micro-averaged, nullable, sum priced cost (scoring.ts:164)
export function regressionAlert(completed: CompletedRunMetrics[]): string | null             // 2 latest completed, largest drop (scoring.ts:230)
```

`caseCounts` (scoring.ts:91) already encodes AC-13's rules over ANY finding set:
must_find → `matchedMustFind`; must_not_flag with empty `findings[]` → every finding
is noise (clean fixture); else noise = findings intersecting a must_not_flag region;
findings elsewhere never penalize precision. The delta module's ONLY job is to
produce the delta finding set + delta dropped count; scoring is then unchanged.

The finding↔finding delta match reuses the SAME notion as `matchesExpectation`'s
range logic — `rangesIntersect(aStart,aEnd,bStart,bEnd)` (scoring.ts:78): file
EQUALITY AND `[start_line,end_line]` INTERSECTION; severity/category/title informative
only (AC-10).

### Reused engine outcome shape (reviewer-core/src/review/run.ts:102)

`reviewPullRequest(...)` returns `ReviewOutcome`:
```
review: { findings: Finding[]; ... }   // GROUNDED (kept) findings
dropped: { finding: Finding; reason: string }[]   // failed the citation gate
costUsd: number | null                 // null if any cost component unknown
```
Per-case cost of a differential run = combine both arms with the run.ts rule
(run.ts:192): `cost = (a == null || b == null) ? null : a + b` (never treat unknown
as 0) → AC-18.

## Risks & mitigations

- **Migration not applied before integration tests.** `*.it.test.ts` provisions
  schema via `runMigrations` (test/helpers/pg.ts:42), so T6 MUST generate the
  migration file (`pnpm db:generate`) or every skill integration test 500s with
  `relation "eval_skill_suite_runs" does not exist`. The implementer generates the
  file (SQL emission, not application); it does NOT run `pnpm db:migrate`. For the
  dev DB, a human runs `cd server && pnpm db:migrate` (MANUAL, AGENTS.md gotcha).
- **Two suite-parent FK columns confusion.** A per-case row must set EXACTLY one of
  `suite_run_id` / `skill_suite_run_id`. Enforced as a service invariant (executor
  always passes `skillSuiteRunId`, never `suiteRunId`, for skill runs). Mitigate
  with an executor unit test and a repo test asserting the FK cascade on skill-suite
  delete.
- **Doubled LLM cost.** A differential run is 2 engine passes per case → ~2× an
  agent suite. Mitigated by reusing `EVAL_RUN_RATE_LIMIT` (10/min) on every skill
  run-start route and surfacing the summed-both-arms cost tile before a run (AC-18).
- **Barrel edit vs "never edit the barrel".** Adding one `export *` line for a NEW
  file is the sanctioned additive extension (L06 did it for `eval-suite.js`,
  index.ts:30); it does not touch existing exports. Called out as an assumption.
- **Untrusted diff / skill body reach the engine.** Both arms feed the engine ONLY
  the stored diff + PR meta + host config; the engine's INJECTION_GUARD +
  untrusted-content wrapping apply, and the delta/scoring path uses NO LLM (AC-33).
  Secrets in `input_diff` are never logged; LLM keys via `LocalSecretsProvider`.
- **Client hooks file contention.** `lib/hooks/eval.ts` and `CaseEditor` are edited
  ONLY in C1; C2/C3 consume them. This is the single reason C1 is a distinct
  foundation slice — do not let C2/C3 also edit those files.
- **Client suite runs on the WSL ext4 mirror** (`scripts/test-mirror.sh client test`),
  never `pnpm test` from `/mnt/e` (TD-010). Package suites run STRICTLY SEQUENTIALLY.
- **Evals gate N/A.** This touches contracts/schema but NOT `.claude/skills` or
  `CLAUDE.md`/`AGENTS.md`, so the `evals/` harness gate does not apply; the green
  barrier is the package suites (server unit + integration, client) + `pnpm arch:check`.
