## Orchestration Patterns
- [2026-06-25] The biggest hidden cost in PARALLEL subagent runs is each implementer/verifier independently re-reading the same template/convention files (template agents, contracts, shared boilerplate). Fix: `implementation-planner` emits a **Shared scaffold (context pack)** section that lifts reusable boilerplate VERBATIM with `file:line`, phases REFERENCE it instead of "go read there", and the orchestrator embeds that pack into each implementer's spawn prompt — pass ready fragments, not pointers. Codified in `.claude/agents/implementation-planner.md` (Working loop "Context-pack rule" + spec template) and `.claude/agents/implementer.md` (Working loop step 1).
- [2026-06-25] Surface skills load ON-DEMAND via the `Skill` tool, not preloaded; only truly always-on skills go in the `skills:` frontmatter (read-only/coverage-focused agents like `plan-verifier` omit the field entirely). Keeps each parallel agent's context lean — it loads only the set for the surface its slice touches; `.claude/agents/implementer.md` / `implementation-planner.md` (frontmatter `skills:` comment).
- [2026-06-25] `effort` is an official PER-SUBAGENT frontmatter field (values `low`/`medium`/`high`/`xhigh`/`max`; overrides the session effort, default = inherit; available levels are model-dependent — `xhigh`/`max` need opus/fable, sonnet caps lower). Tune by ROLE: `xhigh` on reasoning-heavy opus agents (`architecture-reviewer`, `plan-verifier`, `implementation-planner`); keep the parallel `implementer` at `high` so a fan-out of opus workers can't inherit an `xhigh`/`ultracode` session and multiply cost. Gotcha: settings.json `effortLevel` documents only `low`..`xhigh` (no `max`), but frontmatter `effort` includes `max`. Verified vs code.claude.com sub-agents + settings docs 2026-06-25.
- [2026-07-04] Before adding an agent, grep its intended trigger phrases across every existing agent's `description:` — "write a spec" sat inside implementation-planner's description and would have swallowed spec-creator's routing; phrases must stay disjoint, plus an explicit "Unlike <sibling>…" contrast in both descriptions. `.claude/agents/implementation-planner.md` / `spec-creator.md` (description).
- [2026-07-04] Lifecycle flips vs read-only agents: plan-verifier stays Write-less and only EMITS a "Spec status recommendation: ready for `Status: implemented`" line — the main session/user performs the edit. Pattern: let a read-only agent's report RECOMMEND a mutation instead of granting write tools that would weaken its guarantee; `.claude/agents/plan-verifier.md` (Output format).
- [2026-07-04] `docs/specs/SPEC-*` are LIVING specs by decision: spec-creator evolves an existing spec (git = version history) instead of creating successors; `Supersedes` is reserved for conceptual replacements/splits; AC-IDs are append-only with removed ACs marked in place, so plan/test/RTM references never break. `.claude/agents/spec-creator.md` (Living spec policy).
- [2026-07-04] A spawned subagent cannot question the user mid-run, so any "the agent must clarify with the user" requirement is designed as a STOP-AND-ASK two-pass contract: pass 1 returns numbered blocking questions (each with why-it-blocks + a recommended answer) INSTEAD of the artifact, and a re-invocation carrying the answers counts as approval; the `description:` must tell callers to pass known answers (spec path, execution mode) up front to skip the round-trip. `.claude/agents/implementation-planner.md` (Stop-and-ask protocol).
- [2026-07-04] Measuring a multi-agent run in-context undercounts badly (~5–10×): the parent's `<usage>` EXCLUDES subagent tokens and the parent-side `Agent` toolUseResult carries no totals — the only accurate source is the on-disk journals `~/.claude/projects/<slug>/<session>/subagents/agent-*.jsonl` + `.meta.json` (agentType/toolUseId/spawnDepth; nested agents sit flat, parented via toolUseId), where streamed assistant lines repeat one `message.id` with CUMULATIVE usage → dedupe per-field max per id, never sum raw lines. Codified in `.claude/skills/workflow-retro` (SKILL.md gotchas + `scripts/retro_metrics.py`).
- [2026-07-04] Skill vs agent registration is asymmetric: a new `.claude/skills/<name>/SKILL.md` HOT-REGISTERS in the same session (the harness re-lists available skills right after the `Write` — `run-plan` was invocable immediately, no restart/probe), whereas `.claude/agents/*.md` only register in a fresh session (README "Verifying agent triggering"). Availability ≠ auto-triggering: routing is driven by adding the skill to the AGENTS.md skill-checkpoint list, not by SKILL.md description wording; `AGENTS.md` (Skill checkpoint), `.claude/skills/run-plan/SKILL.md`.
- [2026-07-04] Generated/mirrored artifacts (e.g. the client's vendored `@devdigest/shared`, synced by `scripts/sync-shared.mjs`) need an explicit OWNER phase in a multi-agent plan: the contracts phase edited only the server copy, so two parallel wave-2 implementers each hit the broken client typecheck and race-ran the sync on the same generated files. Planner: put "run the sync" inside the contracts phase's disjoint scope; orchestrator: add the drift `--check` to the green barrier; `docs/plans/project-context-folder.md` (Phase 2), `scripts/sync-shared.mjs`.
- [2026-07-04] When a UI phase runs API-parallel with the backend phase that implements its endpoints, the orchestrator must FREEZE the exact routes + request/response shapes VERBATIM in BOTH spawn prompts ("FIXED API contract — do not deviate"), not just mark the phases parallel-safe: in the project-context run P4 (server attach endpoints) and P6 (client hooks against mocked fetch) were built concurrently and converged with zero drift because both prompts carried the same frozen contract. `.claude/skills/run-plan/SKILL.md` (Stage 1), `docs/plans/project-context-folder.md` (Phase 6 "API-parallel with Phase 4").
- [2026-07-04] A production-code defect surfaced by the test-writer gap pass is best routed IMMEDIATELY to the owning wave implementer via `SendMessage` (context still warm) BEFORE running the green barrier, rather than deferring to the Stage-5 fix loop — fixing pre-barrier turned a would-be red barrier + rerun into a single green pass (run-executor trace/status race). `.claude/skills/run-plan/SKILL.md` (Stage 2→3 seam).
- [2026-07-04] `pr-self-review` on a long-lived, incrementally-published branch: the hook's content-addressed marker means every previously PUSHED commit already passed a full-branch review, so when the delta since the last-pushed HEAD is docs-only it is sound to classify and gate ONLY that delta instead of re-reviewing the whole `main...HEAD` code mass — state that interpretation explicitly in the verdict. A code-touching delta still gets its surfaces' full lenses; `.claude/skills/pr-self-review/SKILL.md` (marker contract).

- [2026-07-05] Waves are a scheduling default, not a barrier: spawning a phase's implementer the moment its `depends on:` set is satisfied (impl-p3 right after Phase 1, impl-p5 right after Phase 4, while wave-1 siblings still ran) overlapped waves with zero scope conflicts — disjoint slices make eager launch safe. Codify when editing `.claude/skills/run-plan/SKILL.md` (Stage 1).
- [2026-07-05] Implementer briefs saying "run the relevant test suite to green" produce FULL-suite runs inside phases (~35 min each on WSL for the client suite; impl-p6 AND impl-p7 both did it) that the orchestrator's green barrier then repeats. Spawn prompts must scope it: targeted `vitest run <slice files>` + typecheck only; the full suite belongs to the green barrier alone; `.claude/skills/run-plan/references/spawn-prompts.md` (implementer template).
- [2026-07-05] A context-pack fragment that offers a wiring DISJUNCTION ("add a container getter OR construct in the service — follow the sibling") reliably becomes a review finding: the onboarding-generator implementer picked in-service `new OnboardingRepository(db)`, the only module bypassing the composition-root getter pattern, flagged MEDIUM by architecture-reviewer. Planner rule: DI/wiring choices in a CP must name ONE canonical option (the sibling's exact mechanism), never "A or B"; `docs/plans/onboarding-generator.md` (CP-6), `server/src/platform/container.ts` (repo getters).
- [2026-07-05] `simple-implementation-planner` emits plans WITHOUT the `## Tasks` (`- [ ] T<n> … → AC → test_…`) and `## Traceability matrix` sections that `run-plan` Gate 0 hard-requires — only the reworked `implementation-planner` produces them. Cheapest fix at run time: `SendMessage` the still-warm planner to derive T→AC→test lines from its phase mini-ACs and append both sections; durable fix: teach the simple planner's template the same sections. `.claude/agents/simple-implementation-planner.md`, `.claude/skills/run-plan/SKILL.md` (Gate 0). — RESOLVED [2026-07-05]: the durable fix landed (`480e5b1`) — the simple planner's template now emits `Execution mode` + `## Tasks` (T→AC→test) + `## Traceability matrix`, deriving AC-1..AC-n itself when no spec exists.
- [2026-07-05] An i18n/strings phase must declare dependencies ONLY on phases that INTRODUCE new user-facing strings — in the why-risk-brief run Phase 8 (i18n) waited ~33min on Phase 6 (IntentCard rework) that reused existing keys and contributed zero new ones, serializing the tail; phases editing existing UI are key-neutral unless their task text says otherwise. `.claude/agents/implementation-planner.md` (multi-agent profile), `docs/retros/2026-07-05-why-risk-brief.md` (insight 1).
- [2026-07-05] Decision: `implementer.md` deliberately KEEPS its full-suite Definition of Done (standalone runs have no green barrier behind them); the run-plan spawn prompt narrows it per-run and must SAY so explicitly ("this narrows your standard DoD — targeted tests green is enough"), because a bare "run only targeted tests" contradicts the agent's system-prompt DoD instead of overriding it. `.claude/agents/implementer.md` (Definition of Done), `.claude/skills/run-plan/references/spawn-prompts.md` (template 1).
- [2026-07-05] A rule codified in the planner's own .md does not self-enforce: the phase-size balance rule (landed 07-04 22:28, `3715524`) was violated by the very next plan (why-risk-brief P5 >2× wave median, 07-05). Pair every planning-time rule with a cheap orchestrator-side gate — run-plan now re-checks wave balance pre-spawn and returns the plan for a split via template 7; `.claude/skills/run-plan/SKILL.md` (Pre-flight wave-balance gate).
- [2026-07-06] The "targeted tests only — full suite = green barrier" clause added to the implementer template (07-05 entry above) is ALSO needed by the test-writer gap-pass template, which never got it: in the brief-and-onboarding run the gap pass re-ran the FULL server unit suite (528 tests) + 8 client files to close 3 thin gaps (~23 min for a 3-assertion delta). Any run-plan spawn template whose agent has a full-suite Definition of Done needs the explicit narrowing clause, not just template 1; `.claude/skills/run-plan/references/spawn-prompts.md` (template 2).
- [2026-07-06] The targeted-tests clause must survive SINGLE-AGENT mode too: in the english-only run the orchestrator's spawn prompt RELAXED it ("your slice spans both packages, running both is expected here") because the slice was the whole plan — so the implementer ran both full suites (~40 of its 51 min) and the Stage-3 barrier re-ran everything anyway (client ×2, server ×3 with the flake; ≈38% avoidable wall-clock). "Slice = whole plan" does not change who owns full suites — the barrier does, in every mode; the implementer's targeted set for a deletion/docs plan is just typecheck + touched files; `.claude/skills/run-plan/references/spawn-prompts.md` (template 1), `docs/retros/2026-07-06-english-only-localization.md`.
- [2026-07-06] Machine-specific retro actions are codified as a SPLIT: the checked-in skill gets only a machine-agnostic hook ("obey any local barrier constraints CLAUDE.local.md declares — suite ordering/parallelism, exit-code capture") while the constraints themselves (sequential suites in the one WSL distro, `PIPESTATUS` capture) live in the untracked CLAUDE.local.md, so a machine without the WSL flake is not bound by them. Apply the same split to any future local-only rule — never hard-code one machine's limitation into `.claude/**`; `.claude/skills/run-plan/SKILL.md` (Stage 3), `CLAUDE.local.md` (Test-suite execution / green barrier).

- [2026-07-06] When a plan contains e2e tasks, run-plan's pre-flight should PROBE the e2e prerequisites (`agent-browser open about:blank` actually launches; the package's pnpm gate is approved) BEFORE Stage 1 — in the mandatory-line-range run Stage 3 stalled twice on user-only setup (`pnpm approve-builds` for esbuild, `sudo apt` for Chrome's shared libs), each costing a fail→diagnose→unblock→rerun cycle that one upfront probe would have batched; `.claude/skills/run-plan/SKILL.md` (Pre-flight).

## What Doesn't Work
- [2026-07-05] Editing `.claude/**` process files while a run-plan is in flight in the SAME working tree is pure downside: running agents keep the instructions loaded at spawn/invoke time (edits are never picked up mid-run), and the edits land in the diff-vs-baseline scope that Stage-4 reviewers audit and workflow-retro measures — committing does not help, reviewers diff against the recorded baseline sha. Defer process edits until the run passes review, or use a separate checkout; `.claude/skills/run-plan/SKILL.md` (Stage 4 scope).
- [2026-07-05] Running the three full package suites (server Testcontainers `.it.test.ts` + client + reviewer-core) CONCURRENTLY in one WSL distro at the green barrier flakes with `[vitest-worker]: Timeout calling "onTaskUpdate"` in heavy pre-existing files (`server/test/pulls-by-number.it.test.ts` dropped 3 tests, unrelated to the diff) while the same file passes 5/5 in isolation. Barrier rule: re-run the failing file ALONE before triaging a red barrier as a regression, or stagger the server suite off the parallel batch; `.claude/skills/run-plan/SKILL.md` (Stage 3).
- [2026-07-06] Green-barrier command construction gotcha: piping the test runner through `| tail`/`| head` DESTROYS its exit code — a shell pipeline's status is the LAST command's (`tail` = 0), so a RED suite is reported as exit 0 and only the printed summary lines reveal the failure. In the english-only-localization run, `pnpm test 2>&1 | tail -20` made the background-command notification say "exit code 0" while the output showed `[ELIFECYCLE] Test failed` (a concurrency flake — see entry above). Put the exit code on the RUNNER, not after a pipe: `pnpm test; echo "EXIT=$?"` (then read the tail from the output file), or `set -o pipefail`. This compounds the concurrent-suite flake below: parallel client+server suites in one WSL distro reflaked with `[vitest-worker]: Timeout calling "onTaskUpdate"` (server dropped 1 file / 4 tests, `0 failed`), and re-running the server suite ALONE went 80/80 green 637/637 — reconfirming the "re-run the failing suite in isolation before triaging a red barrier" rule; `.claude/skills/run-plan/SKILL.md` (Stage 3 green barrier).
- [2026-06-25] A `PreToolUse` hook in `.claude/settings.json` does NOT fire for subagents — each subagent runs its own session with its own hooks. A hard per-path write boundary for a subagent is only enforceable via a `hooks:` block in that agent's OWN frontmatter; a `tools:` whitelist limits WHICH tools exist (e.g. no `Write`/`Edit`) but never WHICH paths. Verified against Claude Code docs 2026-06-25 (hooks.md + subagents.md).
- [2026-06-25] Headless `claude -p` auto-routing does NOT fire for the `test-writer` agent: the main agent treats "write/add/cover tests" as a core inline capability and does it itself rather than delegating (two probes with distinct phrasings both returned no `subagent_type`). REVIEW/produce-artifact agents auto-route fine — `architecture-reviewer`, `plan-verifier`, `doc-writer` all routed correctly. So a "does the trigger phrase auto-route?" probe is a valid acceptance check only for delegation-worthy agents; for test-writing, rely on EXPLICIT invocation (name the subagent) and treat agent-type registration (description visible in session) as the validity signal instead. `.claude/agents/test-writer.md`.
- [2026-06-25] The `claude-code-guide` subagent confidently FABRICATES specifics about Claude Code config: asked about per-subagent `effort`, it got the field name right but dropped `max` from the value list and invented a non-existent `permissionMode: read-only`. Treat any single guide-agent's verbatim "doc quotes" as unverified — `WebFetch` the primary code.claude.com page (sub-agents / settings) to confirm exact field names and allowed values before acting.
