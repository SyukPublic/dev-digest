## What Doesn't Work
- [2026-07-08] `skill-quality.ts` must NOT strict-YAML-parse SKILL.md frontmatter: gray-matter's default js-yaml 3.15.0 throws on an unquoted `description` with `: ` (e.g. "Trigger terms: x") — valid for Claude Code — and an unguarded `matter()` lets one such file abort the whole gate. Shipped fix: a tolerant `key: value` engine (`tolerantYaml`) + per-skill `try/catch`, plus `internalLinks` strips code spans so backtick'd example links aren't checked as real refs, plus a soft-WARN on unquoted-`: ` descriptions; `evals/src/skill-quality.ts` (tolerantYaml, internalLinks, evaluate).

- [2026-07-08] A plain `tsx` probe/CLI must import runtime pieces (`runClaude`, etc.) from their submodule (e.g. `evals/src/runtime/run-claude.js`), NOT from the barrel `evals/src/index.js`: the barrel re-exports the case DSL, which imports `vitest`, and importing vitest outside its runner throws `Error: Vitest failed to access its internal state`. The barrel is only for `*.eval.ts` files run under vitest; `evals/src/index.ts`.

- [2026-07-08] On Windows `eval:repeat`/`eval:delta`/`eval:benchmark` all die with `spawn pnpm ENOENT` *before* any model call — `run-vitest.ts` spawned `pnpm` (a `.cmd` shim) via `spawn()`/`execFileSync()` with no shell, and `countTests` swallowed it (prints `? test case(s)`); `eval:quality`/`eval`/`eval:skills` run `tsx`/`vitest` directly so were unaffected. Fix: `shell:true` on both calls in `evals/src/run-vitest.ts` (runVitestOnce, countTests) — resolves `pnpm.cmd` via cmd.exe on Windows (`/bin/sh` on POSIX); Node 24 then emits a benign DEP0190 (shell args concatenated not escaped — safe for these fixed internal args).

- [2026-07-08] Content-tier eval practices must only assert what SKILL.md itself teaches: `skillContent()` injects SKILL.md plus `references/*.md` from a `references/` DIRECTORY only — flat `references.md`/`examples.md` files at the skill root (e.g. onion-architecture) are never injected, despite the README's "full payload" wording; `evals/src/artifacts/load.ts` (skillContent).

- [2026-07-09] A negative practice ("does NOT flag X") is unprovable to the verbatim-evidence judge when the model stays silent about clean code — the case prompt must force the mention ("If a part already follows best practice, say so explicitly"). Likewise a practice must not be narrower than the skill it tests: accept every fix the skill canonically recommends (e.g. refine returning false OR superRefine+ctx.addIssue), else a skill-correct answer fails; `evals/skills/zod/zod.cases.ts` (REVIEW_TASK).

- [2026-07-09] A false-positive-control practice ("does NOT flag X") is only valid if the "safe" fixture pattern is FLAWLESS by the skill's OWN rules — not just free of the one flaw you had in mind. Hit twice: security `enrichNote` carried an accidental IDOR-on-read; drizzle `consumeQuota` used `tx.rollback()` (endorsed by SKILL Example 3) but WITHOUT the try/catch the skill's Constraints section demands, so the model correctly flagged the rollback-handling gap. Before asserting "must not be flagged", audit the pattern against every rule the skill teaches; if in doubt, use a trivially-correct control (e.g. a plain `db.transaction` with no rollback); `evals/skills/security/fixtures/notes-controller.js`, `evals/skills/drizzle-orm-patterns/fixtures/review-writer.ts`.

- [2026-07-09] Keep each judged practice single-quote-provable — one verbatim quote must be able to prove it. A 4-5-clause practice (detect + exploit narrative + fix A + fix B + severity) is flaky: no single quote covers it all, so the judge FAILs it with empty evidence even when the model clearly did the work (confirmed twice — zod guidance, security injection where the exploit was quoted under a DIFFERENT passing practice yet the composite command-injection practice failed). Split into ≤2-clause practices ("flags X — and the fix does Y"); put severity/structure in their own practice; `evals/skills/security/security.cases.ts`, `evals/skills/zod/zod.cases.ts`.

- [2026-07-09] A case failing with `Reached maximum number of turns (1)` while its own trace says `ok (1 turns)` is the JUDGE hitting its limit, not the task: `llmJudge` runs `runContent(..., maxTurns:1)` — the only turn-capped call — and it transiently trips (retry usually clears it). Don't chase the task/fixture; rerun the single case (`pnpm vitest run skills/<s> -t "<name>"`); `evals/src/scoring/llm-judge.ts` (llmJudge).

- [2026-07-09] A guidance practice can only be PASSed if the case PROMPT actually asks for what it checks: the pr-self-review hook/gate practice failed until the prompt explicitly asked "when does it stop me … when I git push?" — the model won't volunteer a peripheral detail (a PreToolUse backstop) unanswered. Make the prompt's question cover every practice's territory; `evals/skills/pr-self-review/pr-self-review.cases.ts`.

- [2026-07-09] An A/B agent eval's discriminating "cites the specific rule" practice must reference the citation FORM the STRICT artifact actually emits — not an invented slug. The committed architecture-reviewer cases demanded identifiers (`reviewer-core-zero-io`, `reviewer-core-ground-findings-gate`, `inward-only-dependencies`, `di-discipline`) that exist NOWHERE in the onion-architecture skill/agent/docs (the skill numbers rules "Onion rule N"; the reviewer-core purity/grounding invariant is prose in `reviewer-core/AGENTS.md`), so BOTH variants fail the practice → non-discriminating. Grep every cited identifier against the real artifact before shipping the case; reframe to the emitted form (`Onion rule 1/3`, the `groundFindings` invariant); `evals/agents/architecture-reviewer/architecture-reviewer.cases.ts`.

- [2026-07-09] Write a skill's eval fixtures in the STACK THE SKILL TEACHES, not the project's stack, when they differ. The `security` skill targets Express/Mongo/JWT but DevDigest is Fastify/Drizzle — fixtures had to be Express/Mongo/React or the skill's concrete advice (`String()` NoSQL cast, `jwt.verify` vs `decode`, `execFile`) never fires and you measure the wrong artifact. Check SKILL.md's stack before authoring and match it; onion/zod/drizzle/pr-self-review DO match DevDigest so those stay DevDigest-shaped; `evals/skills/security/`.

- [2026-07-09] The workflow tier's read-only `WORKFLOW_ALLOWED_TOOLS` (`Read/Grep/Glob/Task/Agent/Skill`) is NOT enforced under `permissionMode:"bypassPermissions"`: during `eval:workflow` the model ran `Edit`/`Bash` and WROTE to the live repo (`server/INSIGHTS.md`) via the engineering-insights activation case. bypass overrides the allow-list, so the workflow tier CAN mutate real files — run it against a throwaway cwd/clone (or genuinely enforce read-only), never treat the allow-list as a write guard; `evals/src/tasks.ts` (workflowTask), `evals/src/config.ts` (WORKFLOW_ALLOWED_TOOLS).

- [2026-07-09] Workflow trace assertions silently fail on Windows: the SDK records `Read` paths with OS `\` separators but the cases (and `stopWhen`) compare forward-slash substrings (`f.includes("server/docs/x.md")`), so a file that WAS read reads as "not read" — and a `stopWhen` that never fires runs the nested subagent to the 240s timeout. Fix = normalize at the single source `reads.push(fp.replace(/\\/g,"/"))` (no-op on POSIX, so it stays cross-platform); `evals/src/runtime/run-claude.ts` (runClaude, Read branch).

- [2026-07-09] The lever that actually enforces read-only under `bypassPermissions` is `disallowedTools`, NOT `allowedTools` (the allow-list is silently ignored under bypass — see the mutation-of-live-repo entry above). `workflowTask` now passes `WORKFLOW_DISALLOWED_TOOLS` (Write/Edit/MultiEdit/NotebookEdit/Bash) so mutating tools are hard-blocked even under bypass; `evals/src/config.ts` (WORKFLOW_DISALLOWED_TOOLS), `evals/src/tasks.ts` (workflowTask).

- [2026-07-09] Positive skill `activation` is non-deterministic even on the subscription/haiku (Anthropic) path: across runs the model flip-flopped between invoking the `Skill` tool and doing the work inline (Read/Glob), and DevDigest's English-only "translate + get approval" rule can suppress the Skill call entirely — so the README's "Anthropic path always invokes the Skill tool" is optimistic. Treat a POSITIVE activation case as `indicative` (log a miss, don't block), keep the negative near-miss a hard assert, and add `stopWhen: skillEngaged` so the session ends before a mutating skill's body runs; `evals/src/dsl/case.ts` (activation branch, `indicative`), `evals/workflow/review-workflow.cases.ts`.

- [2026-07-09] Workflow `trace` subagent-dispatch asserts (`expectSubagents`) are model-dependent on the subscription/haiku path too, not just OpenRouter: `eval:workflow` failed once on `architecture-reviewer` (the model reviewed inline instead of dispatching, running to the turn cap) then passed on a single-case rerun. Unlike `activation` a `trace` has NO `indicative` escape — dispatch is a HARD assert — so `eval:workflow` can flake red on a clean HEAD; rerun the one case (`pnpm vitest run workflow -t "<name>"`) before treating a dispatch miss as a real regression; `evals/workflow/review-workflow.cases.ts` (trace/`expectSubagents`), `evals/src/dsl/case.ts`.

- [2026-07-09] A red QUALITY case sitting near its threshold is not yet a skill regression — baseline the SAME case on the pre-edit artifact first (`git stash push -- .claude/skills/<s>/SKILL.md` → rerun the one case → `stash pop`): onion-architecture "route review" scored 60/80/60/60/80% against its 0.7 threshold across five runs with the failing-practice SET shifting between runs, on both pre- and post-edit SKILL.md. Its practice (b) ("typeof re-checks become redundant") failed ALL five of those runs, then passed (case 5/5) once SKILL.md rule 5 was extended to explicitly teach that consequence — so a never-passing practice can be a SKILL-TEACHING gap, not only a case defect: before rewording/dropping the practice, check whether the skill body actually states what it asserts, and teach it there first; `evals/skills/onion-architecture/onion-architecture.cases.ts` (route review case), `.claude/skills/onion-architecture/SKILL.md` (rule 5).

## Tool & Library Notes
- [2026-07-08] Under pnpm 11.7 the `pnpm` field in `evals/package.json` is IGNORED (prints a WARN on every command) — build-script approval moved to `allowBuilds: {esbuild: true}` in the gitignored `evals/pnpm-workspace.yaml`. But esbuild needs no build here at all: it runs via the `@esbuild/win32-x64` platform optional-dep, so `tsx`/`vitest` work even with no approved build; `evals/pnpm-workspace.yaml`.
